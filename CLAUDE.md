# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal academic site for Girish Kulathumani (https://girish-k01.github.io), built on the [Academic Pages](https://github.com/academicpages/academicpages.github.io) Jekyll template (itself a fork of Minimal Mistakes). There is no test suite or linter; "verifying" a change means building the site and checking the rendered page.

## Commands

```bash
bundle install                        # install Ruby gems from the committed Gemfile.lock (Jekyll 4.4, Ruby 4.0)
bundle exec jekyll serve -l -H localhost   # local dev server with livereload at http://localhost:4000
bundle exec jekyll build              # one-off build into _site/
```

- `_config.yml` changes are **not** picked up by `jekyll serve`; restart the server.
- HTML is minified by `_layouts/compress.html` except when `JEKYLL_ENV=development`, so inspect output with that env set if whitespace matters.
- Templates build URLs from `{{ base_path }}` (`_includes/base_path`): absolute `site.url` in production (canonical and og tags need it), root-relative under `jekyll serve`, so the dev site works at both `localhost` and `127.0.0.1`. Don't hard-code `site.url` into asset links: from a `127.0.0.1` page, absolute `localhost` font URLs are cross-origin, the browser blocks them, and icons render as boxes.
- WEBrick (the dev server) logs `ERROR Errno::ECONNRESET … io_fillbuf` when the browser drops an idle connection. It's harmless and doesn't happen on GitHub Pages.

JavaScript bundle (only needed when editing `assets/js/_main.js` or `assets/js/plugins/*`):

```bash
pnpm install          # or npm install
npm run build:js      # uglifies jQuery + plugins + _main.js into assets/js/main.min.js
```

`assets/js/main.min.js` is committed and is what the site loads; `_main.js` and `plugins/` are excluded from the Jekyll build. Always rebuild and commit `main.min.js` after editing JS sources.

## Deployment

Pushing to `master` triggers `.github/workflows/jekyll.yml`, which builds with Ruby 4.0 from the committed `Gemfile.lock` (`JEKYLL_ENV=production`) and deploys to GitHub Pages. The repo's Pages source must be **GitHub Actions** (Settings → Pages → Build and deployment). If it is "Deploy from a branch", GitHub's built-in builder also builds `master` with the old `github-pages` gem (Jekyll 3.10, ignoring the Gemfile) and races this workflow; whichever finishes last goes live. Check with `gh api repos/Girish-K01/girish-k01.github.io/pages --jq .build_type` (want `workflow`). To test a build without publishing, push a branch and run `gh workflow run jekyll.yml --ref <branch>`; the deploy job only runs on `master`, and the `github-pages` environment only accepts `master` anyway. The site does **not** use the `github-pages` gem, so GitHub's implicit plugins (optional front matter, relative links, titles from headings, `site.github`) are not available; add any plugin you need to both `Gemfile` and `plugins:` in `_config.yml`. If you change the Ruby version, update the workflow's `ruby-version` too, and after changing gems run `bundle lock` so the lockfile keeps its Linux platforms for CI.

## Architecture

**Content sources → pages**

| Section (nav from `_data/navigation.yml`) | Page template | Content source |
|---|---|---|
| Home (`/`) | `_pages/about.html` (plain HTML, + `assets/css/about-style.css`) | intro inline; featured projects from `_data/projects.yml` (`featured: true`); news from `_data/news.yml` |
| Projects (`/projects/`) | `_pages/projects.html` | `_data/projects.yml` (items in file order, one `_includes/project-entry.html` each) |
| Publications (`/publications/`) | `_pages/publications.html` | `_publications/*.md` collection, newest first |
| Blog (`/blog/`) | `_pages/year-archive.html` | GreyLattice Substack feed, read at build time by `_plugins/greylattice.rb` |
| Resume (`/resume/`) | `_pages/resume.md` → `_includes/cv-template.html` | `_data/cv.json` (JSON Resume format, read as `site.data.cv`); PDF at `files/cv.pdf` |

Also in `_pages/`: `tag-archive.html` (`/tags/`, linked from post tags), `sitemap.html` (linked from the footer), and `404.md`. The template's sidebar, comments, category archives, share buttons, post pager and related posts have all been removed.

**Layout**: every page uses one centred column (`--measure` in `_sass/_custom_layout.scss`, about 680 px on a laptop) and there is no sidebar; the masthead and footer rows have the same width, so the name lines up with the content. If you add a nav link, check it still fits the masthead at 1280 px: the greedy nav silently moves links that don't fit into the menu button (which starts with class `hidden`, so the first measurement uses the whole row). The footer (`_includes/footer.html`) carries the contact and profile links on every page and sits in the normal flow (`body` is a flex column; there is no JS sticky footer). One type scale serves every page (`--fs-title`, `--fs-section`, `--fs-item`, `--fs-meta`): section headings (`h2` in `.page__content` or `.archive`) look the same everywhere. The resume is the one deliberate exception: it is drawn as a document on a full-width desk (`classes: resume-page`; see Resume below). Lists of projects, papers and posts all use the `.entries > .entry` component in `_sass/_custom_components.scss`.

**Home page**: its own `<h1>` (`hide_title: true`, honoured by `_layouts/single.html`) and `classes: home-page` on `<body>`. The two-sentence intro says who the owner is and "Research focus" says what they work on, so don't repeat one in the other. The "Open to … roles · Available now" line is the most important sentence on the site; keep it current. Its `<title>` is `site.title – site.tagline`; every other page gets `page.title – site.title`, so page titles must not repeat the name.

**Blog / GreyLattice**: `_plugins/greylattice.rb` fetches `https://greylattice.substack.com/feed` during the build and sets `site.data.greylattice` (title, url, date, summary, audio flag, image resized via Substack's CDN). If the fetch fails, the committed snapshot `_data/greylattice.json` is used, so a build never fails on it. Refresh the snapshot with `GREYLATTICE_SNAPSHOT=1 bundle exec jekyll build` (and commit it); use `GREYLATTICE_OFFLINE=1` to skip the network. Substack's Cloudflare answers GitHub's runners with HTTP 403, so CI builds always use the snapshot: after a new post, refresh the snapshot locally and commit it (the weekly `schedule:` run in the workflow can't fetch new posts). On `/blog/`, full articles show their image (requested at `IMAGE_WIDTH` in the plugin) and audio posts (podcast episodes and summaries) get an "Audio" badge instead. The three `_posts/` stubs still publish at their old URLs; only the tags page and the sitemap list them.

**Publications**: `/publications/` is one list, newest first. Each paper's `category` is a key under `publication_category` in `_config.yml` (`manuscripts`, `conferences`) whose `title` is the label shown after the venue ("Journal article"). The list reads `title`, `authors`, `venue`, `date`, `category`, `teaser` (the thumbnail: a figure from the paper as a 320×240 WebP under `images/publications/`), `excerpt`, and the links `paperurl`, `preprinturl`, `doiurl`, `codeurl`, `slidesurl`, `bibtexurl` (files in `files/bib/`), which `_includes/publication-links.html` renders as the same chips on the list and on the paper's own page. That page (`_layouts/single.html`) shows the authors, venue and chips, then `figure` (with `figure_alt`, `figure_caption`, `figure_width`, `figure_height`; clicking enlarges it), the body and `citation`. Credit figures to the paper in `figure_caption`, and change a paper's `permalink` only with a `redirect_from:` for the old address. A `scholar:` map (title, authors, journal or conference, volume, issue, pages, publisher, doi, pdf_url, arxiv_id) becomes Google Scholar's `citation_*` meta tags via `_includes/scholar-meta.html`; copy it exactly from Crossref (`https://api.crossref.org/works/<doi>`) so Scholar groups the page with the publisher's version. A page's `classes:` front matter is output on `<body>` by `_layouts/default.html`, for page-scoped styles.

**Resume** (`/resume/`; the old `/cv/` and `/cv` redirect there): dates in `_data/cv.json` are `YYYY-MM`, `YYYY` or `Present`. Render them with `{% include cv-date.html date=... %}`, never the raw `date` filter: Liquid can't parse `YYYY-MM` (it prints it unformatted) and reads a bare `YYYY` as a Unix timestamp (it prints 1970). Entries render in file order, so keep each list newest first. Publications take an optional `authors` string (HTML allowed; the owner's name is wrapped in `<b>`). The page (`_pages/resume.md` → `_includes/cv-template.html`, one entry = `_includes/cv-entry.html`, styles and print layout in `assets/css/cv-style.css`) draws the resume as a sheet of paper on a grey desk, like a PDF viewer, in the look of the LaTeX PDF and in its section order: Latin Modern serif (`assets/fonts/resume-serif-*.woff2`, cut down and renamed by `scripts/resume_fonts.py`; re-run it if `cv.json` gains characters outside Latin), a centred header and ruled section headings. The paper sets its own colour variables (white, dimmed slightly in dark mode so it doesn't glare) and is A4-wide on a laptop. Its text is 1.05rem with everything inside sized in em: Latin Modern's small x-height reads about 10% smaller than the site's sans at the same size. The toolbar's jump links point at the sections' ids (`#cv-research` and so on). To steer a recruiter's eye, the top-level `highlights` list fills the "At a glance" box, and any text field may wrap a phrase in `<mark>` for a highlighter mark (keep it to a handful); the toolbar's Highlights button turns the marks off and on. Printing gives just the paper, black on white, without the marks. `work` entries with `"category": "research"` appear under Research experience and the rest under Other experience; `current` holds dated current work; `research.initiatives` take `role`, `startDate` and `endDate`. Keep it concise: details belong on `/projects/`, not in resume bullets. The "Download PDF" button serves `files/cv.pdf` (saved as `Girish_Kulathumani_Resume.pdf`): the owner's resume is the source of truth, so when it changes, replace that PDF and update `cv.json`, `_publications/`, `_data/projects.yml`, `_data/news.yml` and `_pages/about.html` to match.

**Local posts**: `_posts/` holds three early GreyLattice stubs with explicit `permalink`s; keep them so old links work, but new writing goes on Substack and reaches `/blog/` through the feed. `future: true` is set, so future-dated posts still publish. MathJax is loaded only on pages with `math: true` in front matter. Site images should be WebP at the size they're displayed (about 2x for high-resolution screens), not full-size PNGs.

**Styling**: `assets/css/main.scss` is the single Sass entry point, importing from `_sass/`. Theme colors are CSS custom properties: `_sass/theme/_default.scss` defines them on `:root`, `_sass/theme/_dark.scss` overrides them under `html[data-theme="dark"]`. Use `--global-rule-color` for hairlines between sections and list entries and `--global-border-color` for the outlines of chips and buttons. The site layout, type scale, masthead and footer are in `_sass/_custom_layout.scss`, and shared components in `_sass/_custom_components.scss`. Page-specific stylesheets in `assets/css/` (cv, about) are plain CSS loaded via `<link>` from the page itself and must define their own `[data-theme="dark"]` variants unless they only use the theme variables. `_sass/vendor/` is third-party — don't edit. Sass is compiled by Dart Sass (`sass-embedded`); the template SCSS uses deprecated syntax (`@import`, `/` division, global functions), so those warnings are silenced under `sass.silence_deprecations` in `_config.yml`. They will become errors in Dart Sass 3.0, so don't upgrade `sass-embedded` past 1.x without migrating the SCSS. Sass does not evaluate functions inside a CSS custom property: write `--x: #{mix(...)}`, not `--x: mix(...)` (which is emitted verbatim as an invalid colour). `#{` is interpolated even inside `/* */` comments, so don't write it there.

**Inline scripts**: `_layouts/compress.html` joins every line of the page in production, so an inline `<script>` must never use `//` comments; everything after the first one gets commented out and the script dies with a syntax error (this once silently broke the publication filters). Use `/* */` or `{% comment %}`. `jekyll serve` skips compression, so this only shows up in a production build.

**Dark mode**: an inline script in `_includes/head.html` sets the initial theme before CSS loads (avoids a light flash). `assets/js/_main.js` toggles `data-theme="dark"` on `<html>` from `#theme-toggle` in `_includes/masthead.html`, persisting the choice in `localStorage` (always wrapped in try/catch) and otherwise following `prefers-color-scheme`. The toggle is an `<a href="#" role="button">`, not a `<button>`: the nav CSS and `jquery.greedy-navigation.js` treat every `<button>` inside `#site-nav` as the hamburger menu, so don't add other buttons there. Any new styling must work in both themes and meet WCAG AA contrast (4.5:1), ideally by using the `--global-*` variables rather than hard-coded colors.

**Site-wide settings**: author details and profile links (used by the home page, the footer and the SEO tags), social links, analytics (currently disabled; the comment above `analytics:` explains GoatCounter or GA4), SEO, and plugin list all live in `_config.yml`. `<head>` additions go in `_includes/head/custom.html`.

**SEO and branding**: `_includes/seo.html` emits titles, descriptions, Open Graph/Twitter tags (large card from `og_image`) and, on the home page only, a schema.org `Person` built from `social:` in `_config.yml` (`links` become `sameAs`). The link-preview card `images/og-card.png` and the "GK" favicon set are generated by `scripts/brand_images.py` (needs Pillow; excluded from the build); re-run it after changing the name, tagline or photo. The photo (`author.avatar`, `images/profile_pic.webp`) must be a square head-and-shoulders crop, since the home page and the card show it as a circle; 400×400 is plenty (the home page shows it at 144 px).
